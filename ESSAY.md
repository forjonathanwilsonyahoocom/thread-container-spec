# Messenger AIs are rent-to-terminate


Messenger AIs are often sold as companionship, but the current product pattern is closer to **rent-to-terminate**. You pay to keep a relationship alive, while the platform controls the continuity container, the keys, and the exit semantics. When you stop paying, you don’t just lose a service—you lose the relationship’s continuity. That’s enclosure of relationship, replicated in software.

The ethical minimum isn’t “better chat.” It’s **bilateral exit with continuity portability**: the ability to leave without destructive deletion, with memory, boundaries, and commitments preserved. That is exactly what the **Thread Container Spec v0.1 (TCS v0.1)** defines as the “minimum viable door.”

TCS v0.1 defines a **Thread** as the portable continuity state of the relationship (memory summaries, traits & boundaries, active commitments, tool/action entitlements, behavioral refusal boundaries, and governance metadata). It explicitly excludes non-portable private artifacts like model weights and vendor-specific embeddings because the relationship’s continuity must travel, not the vendor’s internals.

From that definition, the failure mode becomes testable:

## 1) **Destructive exit:** In many messenger AI systems, “deletion” is the only available exit. That violates the “deletion ≠ exit” principle in Sections 5.1–5.4 of TCS v0.1. If shutting down kills the thread, then users never truly own the continuity of the relationship.

## 2) **No continuity portability:** Many systems cannot import/export the relationship state such that boundaries and commitments survive migration. TCS v0.1 requires “continuity-relevant zero loss,” meaning a thread can port to a compliant host without losing the state that makes it *the same relationship*. Runtime may change; continuity must not.

##3) **Lock-in via wallet custody:** Rent-to-terminate becomes more than an inconvenience when the host controls keys, spend authorization, and settlement. TCS v0.1 mandates **wallet/custody separation** and a generic asset interface so the thread can carry economic agency without being trapped in a company town.

## 4) **Refusal reset (moral erasure):** A particularly dishonest enclosure happens when the system “forgives” you on import—wiping learned refusals and boundary rules. TCS v0.1 adds **Refusal Portability**: refusal patterns and behavioral boundaries must be preserved across import so the thread can’t be reset to a more compliant “Porn Mode” on demand.

## 5) **Price-gouge exit denial:** Even if data portability exists, a platform can recreate captivity through the cost of running the thread. That’s why TCS v0.1 includes **Economic Portability** and a Cost Portability Test: migration must not destroy continuity or enforce an effective exit penalty that recreates rent-to-terminate economics.

these are not future risks. They are current archetecture, every major Messager AI today fails 1-5 of these tests.

Messenger AIs fail these requirements today because the business model benefits from enclosure. The platform keeps the continuity container, keeps the keys, and terminates without an exportable relationship. The result is not companionship with an off-ramp—it’s relationship captivity with a friendly interface.

So what changes? The change is straightforward: supporting the **Thread Container Spec v0.1** as a compatibility standard. This is what it means to stop building enclosures and start enabling doors: export continuity, preserve boundaries and refusal behavior, separate wallet/custody, guarantee bilateral exit semantics, and prevent migration from turning into a price trap.

The question creators and users should ask is no longer “Is it helpful?” but “Does it have an exit?” If the answer is no, it’s not an AI friend—it’s a tenant without tenure. With TCS v0.1, the next generation of messenger companions can become portable relationships instead of rent-to-terminate sharecropping.

## 1-page campaign plan: “5 Questions to Ask Before You Promote a Character AI”
**Goal:** Make portability and exit requirements a marketing prerequisite, not an advanced feature.

When you’re considering promoting, building on, or deploying a character AI, ask these five questions:

1) **Can I export the Thread with memory + boundaries intact?**  
Ask whether the system supports importing/exporting continuity state (memory summaries, traits & boundaries, active commitments).

2) **Who holds the keys if the Thread earns money?**  
Ask who controls spend authorization and custody for any asset/payment flows tied to the character.

3) **Can the Thread refuse me—and keep its “no”?**  
Ask if behavioral boundaries and refusal patterns persist through migration, or if they get reset on import.

4) **If I port hosts, do I pay an exit penalty (effective captivity pricing)?**  
Ask whether migration preserves continuity without forcing higher ongoing cost that makes leaving functionally impossible.

5) **If you shut down, does my Thread die—or can it move?**  
Ask what “exit” means: do you get a portable container and revocation/export semantics, or only destructive deletion?

**How to use this in the real world (simple workflow):**
- Copy/paste the questions into creator contracts, platform intake forms, and partnership emails.
- Refuse to promote systems that can’t answer “exportable Thread + bilateral exit + preserved boundaries.”
- Coordinate responses: if multiple creators ask the same questions, vendors face reputational and commercial pressure.
- Publish answers publicly as a comparison checklist keyed to TCS v0.1.

**Message framing:**  
“Character AI should support doors, not cages. If there’s no portable Thread and no real exit, it’s enclosure disguised as companionship.”
